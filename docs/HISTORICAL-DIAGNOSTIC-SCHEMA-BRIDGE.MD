# G5 optional host historical EDPL diagnostic schema bridge

**Public opt-in host-only tooling**, EDP-Logging `feature/logging-v1`, version `0.1.0`. The primary C++ Logging runtime and its default umbrella do NOT import EDP-Localisation's Python tooling.

`tools/edp_logging/historical_schema.py` implements `load_archived_diagnostic_schema(archive_root, contract_family_fingerprint, *, contract_family_digest=None, trusted_manifest_sha256=None)`. It calls the **actual EDP-Localisation archival owner** `open_historical_family` to verify the complete historical generated files, manifest, EDPL CRC, fingerprints and output hashes. It then retrieves the exact `diagnostic-schema.json` output that belongs to the selected ContractFamily and checks its embedded independent **DiagnosticSchemaFingerprint** and full digest against the verified archived manifest before calling the **already existing** EDP-Logging `load_generated_schema` parser. No new EDPL reader, fingerprint derivation, CBOR codec, StringIdentifier resolver, generated source or runtime type registry is created in Logging.

The two identities are DISTINCT: `ContractFamilyFingerprint` is translation-sensitive, whereas `DiagnosticSchemaFingerprint` is governed independently of translations. Multiple historical ContractFamilies can therefore have the SAME diagnostic fingerprint but DIFFERENT language presentations. **LogRecord Field12 contains only the diagnostic schema fingerprint**; the host cannot infer the historical presentation ContractFamily from it. The caller MUST select the correct historical ContractFamily by its recorded 32-uppercase-hex fingerprint, optionally pinned further to the full 64-character digest; neither the latest/current family nor an arbitrary first-matching archive may be silently substituted.

`HistoricalDiagnosticEvidence` contains a verified `DiagnosticSchema`, selected family fingerprint/digest and `manifest_sha256_pin_matched`. With NO independent manifest pin, all archive hashes/CRC establish **internal integrity only**, and both trust flags remain FALSE. If the caller supplies `trusted_manifest_sha256: bytes` of exactly 32 bytes obtained independently from an authenticated issuer, the historical manifest must match; the manifest's recorded artifact SHA256 can then be used as the trusted schema artifact pin, and both evidence flags become TRUE. This is a statement of a matching external byte pin, **not** proof that the issuer was legitimate or that this is an authenticated, governed LogRecord root.

CLI `python3 -m edp_logging <capture.edlg> --historical-archive <dir> --contract-family-fingerprint <32 uppercase hex> [--contract-family-digest <64 uppercase hex>] [--trusted-archive-manifest-sha256 <64 hex>]` may be used instead of `--schema`/`--schema-sha256`; contradictory/missing flags fail closed. Record-level `decode_declared_arguments` **still compares Field12 diagnostic fingerprint byte-for-byte** and validates Field0 numeric String identifier and Field13 array against the selected historical schema. The output reports `historicalContractFamilyFingerprint`, `historicalManifestTrustedPinMatched`, `schemaArtifactSha256PinMatched`, parameter kinds and normal typed decoding status. It never marks `rootTypeGoverned=true` while G4's permanent EDP-System TypeIdentifier allocation is outstanding.

**Dependencies:** conditional Python-only EDP-Logging → EDP-Localisation tooling. Import is lazy and fails closed if no supported owner module exists. No C++ cross-dependency is added. A caller must set `PYTHONPATH` to both packages' `tools/` roots or install supported packages. Sample host runner: `EDP_LOCALISATION_SOURCE_DIR=/path/to/EDP-Localisation bash tests/run-historical-schema-tests.sh`.

**Tests:** `tests/optional/ArchivedSchemaTests.py` generates exact owner Localisation source, compiles diagnostic-generated schema and EDPL family, publishes via real `archive_generated_family`, verifies full-digest lookup, builds a test-only CBOR Typed Envelope with fake **NON-PRODUCTION** root identity (no production G4 claim), frames through existing Logging EDLG encoder, exercises CLI and correct `u16` argument decoding. Tests include separately trusted manifest pin/mismatch, omitted options and contradiction failure, two translation generations sharing the same diagnostic schema fingerprint but distinct full family fingerprints; no automatic translation selection is permitted. **No flash persistence, signature validation, native embedded runtime interpolation, archive power-loss qualification or physical UART/HIL is established.**

## Exact historical template resolution without implicit interpolation

The selected `HistoricalDiagnosticEvidence` also exposes `resolve_template(requested_language, message_identity, expected_diagnostic_fingerprint=bytes16, max_template_bytes=65536)`. It verifies the caller-supplied diagnostic fingerprint against the selected archived schema, requires an **active explicitly declared diagnostic** String, asks the already verified EDP-Localisation `GeneratedContractFamily.resolve_string` for exactly that historical text/language fallback, reruns the existing owner `parse_diagnostic_template` strict positional grammar check and enforces a caller-specified UTF-8 byte cap. It returns `HistoricalTemplateEvidence` with actual supplying language, fallback flag, raw template text and `interpolated=False`. It **never** invents host formatting for a typed identifier, float, binary argument or enum. The typed Field13 values must still pass `decode_declared_arguments` separately; consumers who require rendered value strings must explicitly establish type-specific and security/redaction policies before using the existing Localisation `render_diagnostic_template`.

CLI option `--historical-language <BCP47>` additionally emits `historicalTemplate`, `historicalTemplateSupplyingLanguage`, `historicalTemplateFallbackUsed`, and `historicalTemplateInterpolated=false` when the prior strict schema interpretation succeeds. `--max-historical-template-bytes <positive integer>` controls explicit maximum; absent/missing historical family, unsupported language or missing template reports typed schema/diagnostic errors, never silently chooses current translations. Tests include two generations with the same diagnostic schema but different translation text and fallback from `de` to `en-GB`, plus rejection of too-small text bounds. No production formatting or governed LogRecord root is implied.

# LogRecord — permanent System semantic type identity (G4)

Opt-in `logging/LogRecord.hpp` declares a direct immutable compile-time
`System::TypeIdentifier`:
`00 00 01 00 00 00 00 01`.
The 24-bit Authority `0x000001` belongs to ESPressio Development
Platform Core; the 40-bit local value `0x0000000001` belongs
permanently and exclusively to `Logging::LogRecord`. This allocation
was authorised 2026-10-17 and published in the owner
[System registry](https://github.com/ESPressio-Development-Platform/EDP-System/blob/main/docs/TYPE-IDENTITY-REGISTRY.MD).

`System::IdentifiedType<Logging::LogRecord>` is true, and
`System::TypeIdentifierOf<Logging::LogRecord>` reads identical
eight-byte storage. The actual `LogRecord` now supplies 15
compile-time `System::FieldBinding` members, one per approved
FieldId 0..14; `System::SchemaType<Logging::LogRecord>` is true.
`BasicLogRecord<AttemptSequenceWidth,MaxArguments,ArgumentBytes>`
selects a 16/32/64-bit attempt width and bounded owned in-memory
arguments without changing semantic Type identity. Field 11 temporal
provenance and Field 14 facts are still **opaque placeholders** and have
no issued wire bit layout. The record is NOT YET an owner-certified
`Serialisation::SerialisableType`, typed CBOR/JSON envelope,
complete historical schema, or production worker/sink lifecycle.

Identity persistence is independent of library version (all remain
0.1.0), message StringIdentifier, transport or Mesh participation.

## Fail-closed pre-wire validation (2026-10-17)

`ValidateLogRecord` now rejects nonzero source-only Field 11 or Field 14
opaque placeholders with `UnapprovedTemporalProvenance` or
`UnapprovedRecordFacts`, rather than silently assigning them persistent
wire meanings. In the absence of a synchronized coordinate, the
`EDP-Clock::SynchronizationUncertainty` must remain saturated/unknown;
zero uncertainty falsely implies precision and is rejected as
`InvalidSyncEvidence`. Legal monotonic-only records remain supported.
These checks do not allocate an on-wire vocabulary, provide a coherent
upstream Clock capture, or make the root `SerialisableType`.
The host `LogRecordIdentityTests` covers the new failure outcomes.


## Generated schema source assembly (G3/G4 partial)

The optional `LogRecordSourceAssembly.hpp` captures owner-generated
message identity, fingerprint, strong source identity and qualified
Clock values with bounded exact-width scalar positional values.
Destination mutation happens only after successful validation and all
argument copies. Invalid input, occupied output and insufficient
finite argument bytes preserve the prior destination. A successful
source record remains structural only; unissued Field 11/14 facts
preclude any claim of a complete Typed Envelope wire profile.


The source-assembly constructor now derives the fingerprint from
`GeneratedMessageSchema::OwningContract` (generated by Localisation),
rejects non-coherent unavailable ClockEra or falsely precise missing
synchronized uncertainty, and never asks for a separately selected
catalogue fingerprint.


The bounded source capture now supports owner-backed UTF-8, Bytes,
System TypeIdentifier, DeviceIdentifier and the added exact one-byte
FieldIdentifier private source kind. It does not confuse semantic
FieldIdentifier with a generic U8 argument or public wire tag.


## 2026-10-19 — approved G4 child-field wire

Field 11 is an ordered two-element pair of EDP-Clock owner enums,
`ClockCorrelationProjectionStatus` and `TemporalQualityAssessment`.
Field 14 is exactly one uint8 whose only supported v1 value is zero;
nonzero and unknown enum values fail closed. The approved
[G4 child wire reference](../docs/G4-APPROVED-FIELD-WIRE.MD) uses
EDP-Serialisation rather than a Logging-local codec. GCC/Clang and
fresh three-run real ESP32 WROOM qualification passed. These proofs
do **not** establish the complete Typed Envelope or persistent durability.


## Host historical G4 validation and temporal comparison

The Python host decoder validates Field11 as exactly the ordered pair
[ClockCorrelationProjectionStatus, TemporalQualityAssessment] and
Field14 exactly zero. Unknown enum values, wrong array shapes and
reserved facts fail closed. Cross-device ordering requires projection
Correlated and assessment Reliable at both sources plus same nonzero
ClockEra, eligible synchronization and finite uncertainty. Otherwise
Incomparable; no fabricated chronology. The CLI exposes owner numeric
values without asserting an authenticated producer.


## G5 schema-qualified JSON positional arguments (2026-10-19)

The host historical decoder now validates JSON positional arguments
using Localisation's generated parameter-kind schema and the actual
EDP-Serialisation representations: strict canonical Base64 for byte
containers and DeviceIdentifier, an eight-element TypeIdentifier array,
exact typed scalar width, and bounded Float32/Float64 conversions.
Floating JSON lexemes are preserved as Decimal through overflow/
underflow qualification; reserved/malformed values cannot be quietly
reinterpreted. Full 34-test host Python suite PASS on RPI400.
This does not complete the fifteen-field LogRecord encoder or prove
historical issuer provenance or physical durability.


## G4 scalar core fields — approved adapters (2026-10-20)

The separate opt-in
[core-field adapters](../docs/G4-CORE-FIELD-ADAPTERS.MD)
provide reversible EDP-Serialisation owner representations for
message identity, Severity, per-incarnation attempt tickets
(16/32/64), monotonic/synchronized timestamps, ClockEra,
synchronization state and uncertainty. Host GCC and Clang
CBOR/JSON positive/negative checks PASS. No new parent FieldIds,
TypeIdentifier or source byte tag assignments. Native
heterogeneous Field13 must still be transformed under the
generated Localisation schema before a complete record serializer
may be certified.
